# Airport Packages

Current flow extensions in `operations.json`: `curveCorridor` limits cubic reference-point deviation from graph edges (at most 5 metres); `pushbacks` maps stand IDs to explicit connected paths, labels, tug/self modes and optional aircraft types. Self-maneuvers require explicit types and a forward initial heading. Each runway-end configuration may declare `roles` (`arrival`, `departure`) as hard capabilities. `arrivalExits` lists IDs, runway nodes, connected vacate paths and exit speeds. `runwayCrossings` declares a stable ID, physical runway and connected hold-to-hold path; ordinary A* taxi routes cannot enter any runway protected area. Validation checks connection, runway release distance and ground access; aircraft braking-distance and route eligibility are checked when clearing a landing. These additions do not alter geometry bytes and remain game assumptions until sourced.

Scenario traffic optionally sets `approachSeconds`, `approachSeparationSeconds` and `decisionSeconds` (defaults 90/60/8 seconds). The obsolete stationary-arrival distance/wait settings were removed. Go-around scoring uses `scoring.goAround` and is applied once per go-around; the aircraft leaves the area. Aircraft motion samples carry source-edge provenance and the current save behavior fingerprint excludes earlier movement snapshots.

For randomized starts, set `initialTraffic` to inclusive integer ranges such as `{ "departures": [2, 4], "arrivals": [1, 2] }` and leave `initialDepartures`/`initialArrivals` empty. Ranges must fit individual and total traffic caps; actual opening aircraft also obey available compatible stands and their reservations. The engine does not generate more departures at gates after startup: recurring traffic enters as arrivals and later rotates to departure after turnaround. Scripted scenario starts remain useful for tests. Repeated entries in fleet type arrays are weights, not a cycling order. Types are drawn before a compatible free stand so numerous small stands do not dilute widebody weights.

`traffic.intervalJitter`, `traffic.approachJitter` and scenario-level `turnaroundJitter` are optional fractions between 0 and 0.5 (default 0). Timing is uniform around the base within that fraction; approach spacing may extend ETA further. The decision point must be below the minimum randomized ETA. Turnaround applies the type multiplier first and samples once on parking. Saves contain a nonzero uint32 seed and PRNG state; no runtime network/clock randomness is used inside the engine. Changing draw order or the generator requires a behavior fingerprint change, not silent continuation.

The shared engine, map and UI do not contain airport names, runway designators, stand lists or holding-point identifiers. `src/airports/catalog.js` is the explicit bundled catalog. Edinburgh and Frankfurt are the shipped real airports; synthetic fixtures are included only in test bundles.

Each airport directory contains:

- `geometry.json`: real mapped features, OSM node/edge identities, stand lead-in paths, projection and source/license metadata. The original Edinburgh file retains legacy operational fields for byte/save compatibility; the loader overrides those fields from operations rather than treating them as authority.
- `operations.json`: ground name/frequency, physical runway and distinct operational ends, protected width/release distance, curated departure holds/entries and arrival vacate paths, eligible holding points, map bounds and label anchors.
- `scenario.json`: `runwayUses` supplies the initial active ends and `runwayPresets` may provide named selectable configurations. Each use assigns arrivals, departures or both, with optional traffic weights, and must stay within the operational end's declared capabilities. The scenario also contains initial flights, eligible departure stands, callsign prefixes, arrival intervals/capacities, approach and turnaround timing, cleanup timing, scoring, clock and simulated weather. `compatibleAirportRevisions` and `compatibleConfigurationRevisions` may list specifically audited format-2 fingerprints that remain state-compatible after additive changes; they are not a legacy migration mechanism.
- `fleet.json`: versioned aircraft mixes, initial types, stand length/wingspan limits, adjacent-stand exclusion groups, allowed types per taxiway reference and simplified departure-wake delays. Current Edinburgh limits are labeled game assumptions. Missing stand limits reject use, never imply unlimited space.
- `import.json`: optional offline-import descriptor selecting projection, metadata, stand IDs and the adjacent operations/scenario files. No network request is made by the importer.

Load with `createAirportPackage({ geometry, operations, scenario, fleet })`. It validates IDs/references, graph connectivity, mapped holds, pushback paths, ground-only reachability, runway capabilities/presets, connections and declared crossings, fleet/stand/route eligibility, initial traffic, scenario values and map metadata, then freezes the result. Geometry-only import validation can omit fleet data, but GameSession requires it before play. Physical runway occupancy is independent, while opposite operational ends of the same pavement share one owner. Aircraft receive an arrival/departure runway assignment; wake history, landing exits, holds and clearances follow that assignment. During a live change, committed approaches and runway-bound departures retain their assignment; uncommitted departures and new traffic use the new configuration. Gear-based turn clearance, swept-wing collision checks and intersecting-runway dependency groups remain separate engine work.

Package geometry uses local metres (`x` east, `y` south). Runway-end IDs are distinct from displayed numbers and physical runway IDs. Stand IDs may be alphanumeric. Arrival `vacatePath` starts at `arrivalExit`, follows real adjacent graph nodes and ends beyond the runway release distance. Do not infer a safe procedure from a nearby disconnected line or automatically choose the first stand as a runway exit.

## Candidate Imports

```sh
node scripts/import-airport.mjs /path/to/source.osm data/airports/egph/import.json /path/to/new-candidate.json
```

The output must not exist. The importer selects the component containing the configured departure hold, preserves IDs, normalizes duplicate route segments, infers parking-line direction only when exactly one endpoint joins the taxi network, includes explicitly selected stands, validates the resulting package and writes a candidate. Ambiguous loops and disconnected parking markings are rejected rather than joined by guesswork. Review attribution, map/graph quality and operational connections before deliberately replacing published geometry. Changing coordinates or route identities requires an explicit save-compatibility decision. Regenerating the current Edinburgh package from the original OSM extract reproduces its existing geometry bytes and revision exactly.

To add a real airport, curate and validate its package, add an explicit import/catalog entry, then run `npm run verify`. Static geometry copies and the offline bundle are generated by the build. The catalog navigates with an airport query parameter after saving the departing session; a full document navigation disposes old listeners/animation work. Saves are keyed by airport ID. Scenario selection is configured in the package, not yet exposed as a user picker.

## Save Compatibility

Current saves use format 2, including `configurationRevision`, `scenario` (ID/version), `operationsVersion`, active runway uses/changeover state, per-aircraft runway assignments, per-physical-runway owners and per-runway departure-wake state. Audited earlier format-2 snapshots without runway-use state receive the scenario default on restore; this is not legacy-format support. The configuration fingerprint includes fleet settings, aircraft catalog version and behavior revision. Geometry revision is separate; label/weather/clock-only edits do not invalidate progress. Increment the aircraft catalog version when changing dimensions or performance.

The user explicitly declined legacy support and manual game transfer. All 23 archived v1 fixtures are rejection/non-overwrite tests; their bytes remain unchanged. There is no migration or alternate legacy engine. An incompatible snapshot blocks play until the top-bar delete action successfully writes a fresh game. Exclusive browser writer locks prevent competing automatic saves.

Tests use a small vertical runway with unrelated IDs, alphanumeric stands, different schedules/scoring, and an offset coordinate system. It completes both flight cycles and exercises the real UI/map, per-airport switching, persistence and offline packaging. Do not add this synthetic field to the real-airport catalog.
