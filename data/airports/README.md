# Airport Packages

The shared engine, map and UI do not contain airport names, runway designators, stand lists or holding-point identifiers. `src/airports/catalog.js` is the explicit bundled catalog. Edinburgh remains the only real airport shipped; synthetic fixtures are included only in test bundles.

Each airport directory contains:

- `geometry.json`: real mapped features, OSM node/edge identities, stand lead-in paths, projection and source/license metadata. The original Edinburgh file retains legacy operational fields for byte/save compatibility; the loader overrides those fields from operations rather than treating them as authority.
- `operations.json`: ground name/frequency, physical runway and distinct operational ends, protected width/release distance, curated departure holds/entries and arrival vacate paths, eligible holding points, map bounds and label anchors.
- `scenario.json`: active runway end, initial flights, eligible departure stands, callsign/type mix, spawn intervals/capacities, turnaround/go-around/cleanup timing, scoring, clock and simulated weather.
- `import.json`: optional offline-import descriptor selecting projection, metadata, stand IDs and the adjacent operations/scenario files. No network request is made by the importer.
- `compatibility.json`: optional pinned admission for pre-configuration v1 saves. Never update this merely to make incompatible old saves load.

Load with `createAirportPackage({ geometry, operations, scenario, compatibility })`. It validates IDs/references, graph connectivity, mapped holds, pushback paths, ground-only reachability of all stands, runway entry/exit positions, arrival vacating, scenario values and map metadata, then freezes the result. It rejects unsupported unprotected runway-crossing edges. The engine currently supports one physical runway and one configured active end at a time. Multiple runways, protected crossing clearances and realistic aircraft-size eligibility remain separate engine work, not a matter of adding JSON.

Package geometry uses local metres (`x` east, `y` south). Runway-end IDs are distinct from displayed numbers and physical runway IDs. Stand IDs may be alphanumeric. Arrival `vacatePath` starts at `arrivalExit`, follows real adjacent graph nodes and ends beyond the runway release distance. Do not infer a safe procedure from a nearby disconnected line or automatically choose the first stand as a runway exit.

## Candidate Imports

```sh
node scripts/import-airport.mjs /path/to/source.osm data/airports/egph/import.json /path/to/new-candidate.json
```

The output must not exist. The importer selects the component containing the configured departure hold, preserves IDs, includes only explicitly selected stands, validates the resulting package and writes a candidate. Review attribution, map/graph quality and operational connections before deliberately replacing published geometry. Changing coordinates or route identities requires an explicit save-compatibility/migration decision. Regenerating the current Edinburgh package from the original OSM extract reproduces its existing geometry bytes and revision exactly.

To add a real airport, curate and validate its package, add an explicit import/catalog entry, then run `npm run verify`. Static geometry copies and the offline bundle are generated by the build. The catalog navigates with an airport query parameter after saving the departing session; a full document navigation disposes old listeners/animation work. Saves are keyed by airport ID. Scenario selection is configured in the package, not yet exposed as a user picker.

## Save Compatibility

Flight-state schema remains v1, with additive `configurationRevision`, `scenario` (ID/version) and `operationsVersion` envelope fields. The existing geometry revision remains separate. The configuration fingerprint covers operational runway/hold data and simulation scenario settings; label, weather and displayed clock-only edits do not invalidate operational progress.

The 23 archived v1 fixtures contain no new envelope fields. Only the pinned unchanged Edinburgh geometry/configuration admits them, preserving every aircraft/route/clearance and its continuation. Current saves with mismatched metadata are rejected without replacing the original bytes. A recovery copy is attempted; automatic/command saves remain disabled until an explicit Restart. General version migrations, recovery downloads, save export/import and cross-tab single-writer ownership are still planned.

Tests use a small vertical runway with unrelated IDs, alphanumeric stands, different schedules/scoring, and an offset coordinate system. It completes both flight cycles and exercises the real UI/map, per-airport switching, persistence and offline packaging. Do not add this synthetic field to the real-airport catalog.
